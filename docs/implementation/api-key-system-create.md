# WormholeSystems topology reconciliation

## Authorization and trust boundary

`PUT /api/v1/maps/:mapId/wormholesystems/topology` is the dedicated topology route. A `wormholesystems_sync` API key is explicitly bound to one Nexum map and inherits the existing read, events, and content-write capabilities, but topology changes are allowed only through this route. No human approver, per-change approval flow, or separate source-signing/control plane is involved.

The map-bound key is held only by the trusted Galaxy service. Its map binding plus that service trust is the authorization boundary; Nexum does not independently authenticate WormholeSystems upstream. Do not add source identity to the key UI or key metadata. Galaxy supplies `sourceIdentity` as a validated canonical ownership namespace in the form `wormholesystems:${JSON.stringify([origin, selectedSourceMapId])}`. Nexum validates that canonical form and uses the exact identity to scope ownership, checkpoint, update, and delete queries. One identity can never mutate or delete rows recorded under another identity.

Galaxy may submit only after it has validated a complete full-map fetch, including response fan-out, member/reference consistency, and the exact target map. The request's `snapshot.complete` is an attestation from this trusted service, not independently verifiable source proof. Complete map membership represents topology presence only; it does not claim a system or connection is physically live. `fetchedAt` is stamped by Galaxy after the validated full-map fetch completes. Nexum rejects missing, malformed, future-dated, or more-than-10-minute-old timestamps. `snapshot.maxAgeMs` is not accepted or client-configurable. Per-row observation timestamps and fabricated active/status values are not part of the request contract.

## Request and ownership rules

The body is strict and bounded: at most 100 systems and 2,000 connections; source IDs are bounded trimmed strings, EVE system IDs are positive valid Nexum SDE IDs, positions are finite and bounded, and source connection fields `connection_type` / `ship_size` must use Nexum values (`standard`, `gate`, `jumpgate`, `cyno`; `small`, `medium`, `large`, `xl`). No unsupported defaults are invented. Unknown fields, duplicate identities, invalid endpoints, incomplete membership, and invalid freshness evidence are rejected before topology mutation.

Only rows transactionally created and recorded in `wormholesystems_topology_ownership` are eligible for source updates/deletes. Existing manual rows are never claimed. WormholeSystems is authoritative for the bound map's source-owned topology, including supplied system positions; Nexum-only annotations remain Nexum-owned. Reconciliation protects non-position managed-field edits, ambiguous endpoints, dependencies, and manual data as specified below. Omission from a complete validated membership snapshot is topology absence for that source, not a physical-liveness assertion. Publish `map.resync` only after a committed topology change.

## Source-owned system reconciliation

Apply these rules in dependency order within the existing map-locked, checkpointed transaction:

1. Validate the complete, fresh snapshot and its source identities before mutation. Reject malformed, partial, non-finite, or out-of-bounds coordinate input; accept coordinates only as a complete pair, normalized to Nexum's existing `Math.fround` precision. Never infer a source row identity or EVE identity from coordinates.
2. Resolve system ownership by the exact target map, canonical `sourceIdentity`, and unambiguous `sourceSystemId` association. Never discover, adopt, claim, or move an unowned/manual row by EVE ID, matching coordinates, or any other apparent match. Preserve the existing conflict behavior for ambiguous identity or ownership.
3. For an already owned system, check ownership identity and non-position source-managed fields against their managed baseline before writing anything. Drift in `eveSystemId`, `name`, or `systemClass`, or an ownership-identity mismatch, remains a conflict: preserve the whole row and its baseline, omit its source-to-row mapping, and do not reconcile dependent source-owned signatures or connections through it. This also applies when position drift is present simultaneously; source coordinates must not mask the conflict or partially update the row.
4. If ownership and those non-position baseline fields are consistent, a supplied validated coordinate pair is authoritative even when Nexum's current position differs from the recorded baseline. Update the existing row's `position_x`/`position_y` to the source pair and refresh its owned baseline coordinates in the same transaction. Keep its system-row UUID and source-to-row mapping stable so dependent source-owned signatures and connections can reconcile against that row without position-induced conflicts or replacement. Other ordinary source-managed changes remain subject to the existing consistent-baseline rules.
5. If source coordinates are absent/null, preserve the row's current target position; do not reset, infer, or overwrite it. Exclude position mismatch alone from managed-drift blocking in this case, and do not make an absent pair into a new authoritative baseline. Continue independent signature association validation, safe-deletion checks, and existing conflict handling for all other ownership and managed-field conditions.

An incoming coordinate update may modify only `position_x`/`position_y` and the corresponding owned baseline coordinates on an otherwise eligible system, in addition to ordinary permitted source-managed updates. Preserve Nexum-only notes, labels, `custom_labels`, intel, status, `is_home`, locked, tag, alias, and region metadata on that row; keep notes separate from source-owned data. Do not change system, signature, or connection row identities merely because position changed. Never rewrite manual/unowned system positions.

## Ordering and retry behavior

Galaxy serializes source fetch/apply per map in its process. Nexum additionally serializes applies by locking the map row and persists `(map_id, source_identity, fetchedAt, digest)` in `wormholesystems_topology_checkpoints`. The checkpoint comparison, topology reconciliation, and checkpoint advance share one database transaction.

The digest covers the canonically normalized full validated payload, including desired IDs/fields and `fetchedAt`; list order alone does not change it. A timestamp older than the accepted checkpoint returns 409. The same timestamp and digest is a successful no-op. The same timestamp with a different digest returns 409. A later fresh timestamp can apply and advance the checkpoint even if topology itself is unchanged; failed transactions never advance it. This protects against out-of-order Galaxy submissions using trusted Galaxy's per-map serialization; it does not establish upstream source ordering or detect an upstream rollback. No generation counter or run journal is used.

## Validation

Run Nexum server/web builds, focused topology service tests, the topology integration test, and `git diff --check`. Report an integration database skip as skipped; it is not a passing database-backed authorization/ownership check. Acceptance cases must demonstrate:

- A fresh, complete snapshot for an unambiguously owned system with position-only drift sets the row to the source coordinates, refreshes its owned position baseline atomically, and preserves its UUID, notes, labels, `custom_labels`, intel, status, `is_home`, locked, tag, alias, and region metadata. Its source-to-row mapping remains valid; unchanged associated signatures and connections reconcile normally without duplicate creation or deletion or changed row identities.
- A stale/incomplete snapshot cannot override positions; a complete snapshot with absent/null coordinates preserves current target positions and does not block mapping merely because those positions differ from the saved baseline. Malformed/partial/non-finite coordinates remain rejected.
- A row with non-position managed or ownership-identity drift still conflicts and is not mapped for dependent reconciliation even if its position also differs; neither the system row nor its baseline is partially changed.
- An exact EVE-system or coordinate match to an unowned/manual row does not claim it or rewrite its coordinates; ambiguous source/ownership/EVE identities are not resolved by position inference.
- Map binding, source-identity isolation, lock/checkpoint replay rules, failed-transaction atomicity, independent signature association checks, safe deletion, and committed-change-only resync behavior remain covered.
